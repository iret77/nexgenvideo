Pipeline phase progress

Normative progress treatment for a host-executed pipeline phase. This specializes the existing transcript activity entry; it does not add a second pipeline or a new destination.

Rules

  • While run_phase is active, its generic activity row becomes one compact, always-expanded progress card at the position of that tool call.
  • The card names the phase, original user-facing source filename, current operation, completed stage count, total stage count, and the next operation. Never expose storage hashes.
  • Progress advances only on runner-emitted stage boundaries. No invented ETA, percentage, or endlessly animated fake completion.
  • The phase list remains the canonical pipeline overview. It only marks the current phase as active; it does not duplicate detailed progress.
  • While a phase runner is active, its row shows Running; every gate mutation for the project is unavailable on every row and in every writer path. When the runner settles, the current row shows Approve disabled until the canonical artifact and lineage pass the same structural gate used by the agent.
  • When finished, the card collapses to the normal completed activity row. On failure, it remains a concise failed row whose existing disclosure reveals the error.
  • All visible copy follows the app UI language.

States

  • Running: phase + file + current stage + linear overall progress + next stage.
  • Completed: checkmark and concise phase-specific completion label.
  • Failed: error marker and concise phase-specific failure label; technical detail stays disclosed.

Tokens

Use existing AppTheme background, border, text, status, spacing, font, radius and animation constants. The progress fill uses AppTheme.Accent.timecodeColor.

Acceptance criteria

  • During Audio Analysis the user can answer, without expanding anything: what is running, on which track, which operation is current, and how many declared stages are complete.
  • The displayed stage and progress count come from runner events, not model narration or timers.
  • Disconnecting and reconnecting the MCP client does not start a second phase job or lose the original job's progress.
  • No gate control is actionable anywhere in the project until the active phase settles; approval is enabled only if the completed artifact passes its structural gate.
  • The UI remains one compact transcript element at narrow Agent-panel width.
