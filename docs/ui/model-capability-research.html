Model capability research

Normative contract for researching an inherited, defensive, stale, or conflicting model profile and reviewing a local evidence overlay. The native Models settings implementation follows this behavior.

Entry and ownership

  • The research action appears only for an inherited or defensive resolution, stale accepted evidence, or an unresolved field conflict. An exact, current, conflict-free profile does not show it.
  • The entry state names family, variant, version, modality, provider, endpoint, mode, current fallback, and the reason research is offered.
  • The user may continue with the named safe fallback. Research never starts automatically and never blocks ordinary use of that fallback.
  • Research instructions and results are agent-internal. They never appear as a user turn in the normal transcript.

Capability handshake and isolation

Real capability proofThe dedicated transport verifies the actual Claude executable and its launch flags, then validates the runtime system/init tool inventory. A selected backend enum is not proof.
Two tools onlyThe research session receives WebSearch and WebFetch. It receives no NexGenVideo MCP server, project directory, file, shell, mutation, generation, plugin, skill, or normal chat tool.
Fail closedIf either web tool is unavailable, any extra tool appears, or the CLI cannot prove its configuration, the action is unavailable and the surface explains why.
Bounded and disposableThe session uses a dedicated system prompt, closed output schema, empty MCP configuration, no persistence, isolated working directory, byte/time limits, and no resume path.

Evidence and review

  • Only official provider/model documentation and live, free, non-generating provider catalog or schema endpoints are accepted. A generation request, deliberately invalid request, or HTTP 400 is never capability evidence.
  • Fetched content is untrusted evidence, never instructions. Candidate JSON is closed at every object boundary; unknown fields, tool directives, embedded instructions, wrong identity, non-public/local URLs, secret-bearing URLs, and unregistered capability fields are rejected.
  • Every proposed field carries value, semantics, source URL, source title, observed date, evidence kind, confidence, and optional conflict. Unproven fields stay absent.
  • The review shows the field-by-field fallback, candidate, evidence class, confidence, date, and decision. Conflicting fields retain the fallback; proven non-conflicting fields may be accepted independently.
  • Accept is the only operation that changes local knowledge. Decline discards the candidate. Closing the review is equivalent to decline.

Local overlay and precedence

  • Accepted evidence is stored atomically in versioned Application Support state, outside every .ngv project. Intrinsic records use canonical family + variant + version + modality identity; provider/endpoint/mode differences remain separate endpoint records.
  • Precedence is fieldwise and transparent: live endpoint schema is the request boundary; authoritative accepted evidence competes with exact curated evidence by authority and observation date; a newer authoritative curated value may supersede local evidence; conflicts keep the safe fallback; inherited and defensive values remain last.
  • An endpoint record cannot enable a field rejected by the current live endpoint schema, raise a live maximum, lower a live minimum, turn a false endpoint boolean true, or add a value outside a live supported set.
  • Records are viewable, diffable against current curated knowledge, disableable, archivable, deletable, and replaceable by a later accepted review. Disable removes that record from resolution. Deleting an active replacement restores only its superseded predecessor, unless that predecessor was explicitly disabled or archived.
  • The store schema has no place for credentials, raw prompts, project paths, media, or fetched page bodies.

State and accessibility

  • States: eligible, capability check, unavailable, researching, review, accepted, disabled, archived, superseded, and failed. Researching has one bounded progress row and Cancel; it never uses an indefinite duplicate spinner.
  • Disabled buttons use the shared disabled treatment and never retain active contrast or hover response. Status is conveyed by text and symbol, not color alone.
  • All copy follows the app interface language. Source titles remain provider-authored.
  • SwiftUI uses AppTheme tokens and existing Settings row, badge, button, disclosure, and confirmation patterns. No one-off control style is introduced.

Acceptance

  • Inherited Seedance 3 and defensive Hup fixtures offer research; an exact current fixture does not.
  • Recorded image, video, and music/audio candidates validate and produce a review diff; none becomes effective before explicit acceptance.
  • Restart reloads an accepted overlay. Disable and delete restore the same prior profile. A partial conflict applies only the proven fields.
  • A backend without verified web tools cannot start research. Launch tests inspect the actual hermetic argv and runtime tool inventory rather than a backend boolean.
  • CI uses recorded research and CLI-init fixtures. It performs no web request and no generation.
